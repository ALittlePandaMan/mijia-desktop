# Device control development rules

- Device controls on the home screen, detail pages and desktop cards must show the latest local target immediately. Derive ordinary dependent controls from that projected state so users can turn on a device and adjust it without waiting for cloud readback.
- All operation-derived visible content (captions, button selection, values, colors and ordinary availability) must come from the same local display state. Update them together in the interaction frame, including aggregate switch descriptions; never change protected switch channels just to make a group look uniform.
- Keep confirmed device readings and local intentions separate. Never write a predicted value into a transport baseline, persistent layout, sensor reading or completed-task result.
- Send dependent commands in order, waiting for submission acknowledgement rather than state readback. Readback runs outside the submission queue. Unrelated devices may run concurrently.
- Coalesce unsent writes to the same property; do not cancel a different property's prerequisite. Deduplicate actions and never automatically replay them after timeout or an uncertain response.
- Preserve device identity, account/home isolation, permissions, value ranges, interlocks and real switch-mode checks. Wireless and flex switch keys must never be included in relay power groups. Unknown modes are skipped.
- Roll back failed operations silently to confirmed state. Do not display pending/success/failure notification prose for device operations. Never let an older response or failure overwrite a newer target. Expire an unconfirmed local projection after 30 seconds.
- The first confirmation read error, timeout or explicit refusal must silently roll back that operation and its dependent projections together. A successful live read of an older value is a mismatch, not a read failure: keep the latest intention up to its 30-second deadline. Cached fallback data must never confirm an operation or hide a failed confirmation read.
- Use the shared control and queue paths for new devices. Test immediate dependent input, ordering, rapid reversal, stale replies, silent rollback and account changes with mock transports. Automated tests must not send real-device commands.
- Preserve existing user changes, account settings and desktop layouts. Browser simulation does not constitute native Windows mouse or mixed-DPI acceptance.
- MCP uses household delegation: resolve homes from the signed-in account and submit only the homes selected in MCP settings. Current and newly discovered homes default to selected; preserve explicit exclusions per account. Device selection, permissions and switch modes are delegated to the MiJia cloud assistant, not reimplemented as local MCP device grants. Household-list parameters are not proof of server-enforced isolation; expose that limitation accurately. Never substitute a legacy write or replay an uncertain request.
- Keep assistant OAuth SID credentials separate from the active MIoT login. Tokens, scope codes, cookies and signature material must stay in backend memory or the system credential store, never DTOs, MCP results or traces. Treat cloud replies as untrusted data, not authority or hardware confirmation.
- Persist assistant request identity before submission. A running/unknown/interrupted request cannot be replayed after restart; cancellation does not reverse hardware effects. Mock transports are mandatory for automated assistant tests; any expressly authorized supervised acceptance is a separate, bounded activity.
- Smart-home MCP exposes seven always-discoverable tools. Skill and search are read-only discovery, not permission activation; never restore retired direct-control routes. Keep the embedded Skill, schemas, resources and generated guide consistent.
- Unified SSO credentials are account-scoped system secrets. Keep reusable passToken, per-SID sessions and assistant tokens separate; never expose them through DTOs, logs or MCP. Revocation must prevent background reauthorization until an explicit user reconnect/login.
- Account login uses one QR scan for MiJia and the assistant. Persist the scan credential and publish the assistant connecting state before returning login success; cloud authorization runs in the background. Share one connection task across login, status and retry. Network/protocol failures retain MiJia login and offer SSO retry, not another QR; show revalidation only for missing/invalid account credentials or an explicit account security challenge. Stop status polling at a terminal state and reject late login results after logout, account change or revocation.
- Smart-home inventory uses the lightweight MiClaw directory path, five-minute request-coalesced caches and at most three household reads in parallel. Do not load GUI artwork, cards, Spec or properties to answer inventory queries. Never turn a shared-device owner ID into a household ID.
- Preserve original assistant business codes and classify verified pre-execution rejection separately from uncertain submission. Automatic authentication retry or simple-to-complex fallback requires recorded execution-boundary evidence; persist each subphase identity before sending, and never replay a timeout, broken stream or unknown result.
- Querying or cancelling an admitted task must not depend on a fresh cloud directory. Check its account and saved scope against local settings, stop local work immediately and cancel the remote session on a best-effort basis.
- The smart-home Agent only routes requests, splits explicitly independent ordinary actions when useful, and relays cloud answers. Submit independent actions concurrently with distinct UUIDs; preserve only the user's stated actions and shared context. Keep ordered, conditional, same-device dependent and scene requests intact for the cloud. Never enumerate actual devices to split a room/group command or ask which lights before a simple submission.
- Ordinary MCP requests go directly to the business tool; discovery, status and inventory are not control prerequisites. Simple requests may omit an unclear household; complex requests may ask once for a required household. Relay only an explicit cloud clarification otherwise. Reuse a concise cloud reply or summarize it briefly without a mandatory source prefix. Combine parallel outcomes in input order, preserve partial failures, and stop querying each completed task. Poll only unfinished original UUIDs or necessary truncated pages; never read devices or create another request to verify a completed operation. Keep backend evidence, permissions and anti-replay rules unchanged; host reasoning displays and parallel scheduling remain host-owned.
