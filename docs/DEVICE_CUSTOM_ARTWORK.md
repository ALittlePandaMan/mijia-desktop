# 米家自定义设备图标

设备支持上传封面和选择米家内置图标两种形式，来源优先级为：`devPicInfo.logo`、`subclass_id` 直接图片地址、`subclass_id` 数字编号解析出的图片、默认卡片图和型号产品图。

此前只处理了图片地址，漏掉了数字编号。2026-11-10 只读检查确认“电脑”返回编号 26、“小明插座”返回编号 53，没有 `devPicInfo` 图片。米家内置目录中的 26 为电脑，53 为投影仪；因此修改已经保存到云端，桌面端却回退到了型号默认产品图。

`Cloud::devices` 在设备分页中按设备标识收集数字或数字字符串选择，随后通过米家原版 `POST /v2/device/switch_subclass`、空对象参数读取目录，用 `id` 匹配 `proxy_category_icon`，写入该设备的 `customIcon`。这条路径只读取目录，没有调用修改图标的接口。两台同型号设备可使用不同图标；直接上传的封面仍优先。选择恢复为 0 或清空时，下一次设备清单不再保留之前的编号绑定。未知编号或图片加载失败沿用现有默认图后备链。

目录保留在当前认证 Cloud 实例内，成功缓存 5 分钟，失败等待 1 分钟后再读；并发清单读取共用目录锁。登录失效继续交给原有会话处理。每次刷新清单重新读取设备选择，产品图缓存不覆盖自定义图标，图片保留键包含完整来源列表。不持久化图标签名 URL，不按名称或型号猜测所选图片。

证据来自保留的原版米家 APK，SHA-256 为 `18254c5abe2485a7f60150e5ed8cbddb1c88991f6076142e99a3740c9e88ba14`：`Device.parseFromJSONObject` 使用 `optString(subclass_id)`；`kk3.OooOO0O` 读取目录；`arb.OooO0O0` 解析 `id`、`proxy_category_icon`；`t2b.onSuccess` 将所选编号存回设备。APK 身份由 REA 读取，具体类通过已有 JADX 辅助工具做静态导出；没有执行 APK。

5 项 Rust 图标回归测试通过，覆盖数字与字符串、同型号不同图标、上传封面优先、切换及清空选择、未知编号和异常目录。修复后的真实业务层只读读取已确认两个设备分别获得电脑、投影仪图片，且与产品默认图不同。原始图片解码检查通过。最终桌面显示与交付记录见 `.tools/custom-icon-sync-verification.json`、`.tools/custom-icon-sync-delivery.json`，静态及只读协议证据见 `.tools/custom-icon-sync-provenance.json`。

最终签名包已在本机替换并正常重启，4 项真实客户端只读检查全部通过：“电脑”与“小明插座”均来自 `device-custom` 并成功解码，分别显示显示器和投影仪图片；切换房间后保持正确。未修改米家中的图标选择或控制设备，临时验证端口已关闭。
